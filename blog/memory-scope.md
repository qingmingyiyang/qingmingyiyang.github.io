# 做记忆工作台之后，我决定先缩小问题

2026-09-11 · 产品复盘 · Chriptmas OS

根据个人项目经历整理，文字与实现由 AI 协助。

## 最初只是想把资料找回来

做 Chriptmas OS 的起点，是我自己的资料整理需求。文章、文档和讨论散落在不同地方，归类不统一，回找出处麻烦，临时交给 Agent 使用还要重新整理。我希望做一个工具，让整理过的资料能够被未来的任务继续调用。

这个需求逐渐长出了两条路径：一条是提取和归档知识，另一条是用工作台承接任务。两条路径都有吸引力，也容易让功能范围越扩越大。

## 多个实现层放大了范围问题

原型采用 React 页面、Electron 桌面壳和 Python 本地服务。三者组合本身并不能说明方案不合理，真正的问题是，当资料管理、交互和任务能力一起扩展时，接口和状态需要同时对齐。我当时对整体体验的要求很高，但没有把所有链路收敛到一个足够小、能稳定验收的目标。

有些整理和交互功能曾经能够演示，整体 Agent 目标却没有达到我的要求。因此，这段经历更适合被解释为一次范围判断和复盘。把局部页面可用写成整个系统成熟，会掩盖最值得吸取的经验。

## 把两种能力分开看

知识归档回答的是：资料来自哪里，提取了什么，之后怎样找回。任务工作台回答的是：当前要完成什么，能调用哪些工具，任务执行到哪一步。它们可以相互支持，也各自需要清晰的输入、输出和失败处理。

我的取舍是，先把归档和提取作为核心脉络。原文与整理结果分开保存，判断和事实分开表达，让资料保留回溯的可能。至于自动规划、多角色协作和更多集成，可以在基本链路获得证据之后再考虑。

## 下一轮怎样验收

我计划从一条小流程开始：输入一段资料，保留来源，提取结构，由人核对后保存，之后能找回原文并复制给 AI。这里每一步都需要可观察的结果。原文是否保留？修改整理结果后，是否仍能看见它的依据？查不到资料时，界面能否诚实地说明？

这只是下一轮验证方案，尚不能宣称重构已经成功。本次主页附带的上下文卡片，是这一思路的独立小演示：先由人整理，再生成 Markdown。它暂时没有自动提取和检索能力，也没有替代旧系统。

## 我会继续记录什么

后续需要记录的，是输入材料、失败现象、个人判断、AI 修改和复验结果。过去没有完整保存真实模型任务的成功、失败、人工介入、成本和时延，所以目前只能保留定性复盘。下一轮先把记录做好，才有机会判断修改究竟改善了什么。
